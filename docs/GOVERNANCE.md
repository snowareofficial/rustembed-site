## 权限矩阵（一页速查）

| 动作 | 群友 | 贡献者 | 管理员 | 群主 |
|---|---|---|---|---|
| 投文章 / 文档页（PR） | ✅ | ✅ | ✅ | ✅ |
| 合并 PR | — | — | ✅ | ✅ |
| 改制度 / 契约 / 引擎 / 站点配置 | — | — | ✅ | ✅ |
| 发布、回滚、紧急下架 | — | — | ✅ | ✅ |
| 授予 / 回收写权限 | — | — | 需两名以上同意 | ✅ |
| 任免管理员 | — | — | — | ✅ |

三处权限互相独立：**QQ 群身份 ≠ 仓库权限 ≠ 发布权限**。GitHub 侧不给人写权限（只由 CI 更新）。

## 制度怎么改

1. 提 PR，只动一个制度文件；描述里写「改了哪条、为什么、影响谁」；
2. 至少 1 名管理员审核；涉及权限、下架、隐私的改动需**两名以上**管理员同意；
3. 合并后下一次构建即上线，并在 PR 里 @ 受影响的成员；
4. 制度生效日期 = 合并日期；旧版本可从 Git 历史查（不单独维护版本号）。

## 制度的机器可读部分

尽量让规则**能被构建脚本检查**，而不是靠人记：

- 字段必填与类型 → `site/content/contracts/blog.sml`（错误码 `E-CONTRACT-*`）
- 附件类型、体积、图片是否存在 → `engine/build.py`
- 产物不变量（无脚本注入、锚点齐全、无内部字段泄漏）→ `engine/check.py`
- 契约语义回归 → `engine/tests/test_contracts.py`

规则一旦能被检查，就写进上述位置，制度文档里只保留「为什么」与流程。

## 定期复核

每半年（6 月 / 12 月）由管理员复核一次：权限名单是否仍然有效、制度是否与实现一致、
`engine/check.py` 是否需要新增不变量。复核结果在群里公示。
